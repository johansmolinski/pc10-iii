# The MEGA65 shell (M2M) of the PC10-III core

Status: 2026-10-21, branch `m2m-shell`. The framework around `pc_system`:
clock, memories, video, keyboard, audio, menu, firmware, Vivado project and
the remote build. Until `rtl/system/pc_system.sv` exists, a stand-in
(`CORE/stub/pc_system.sv`) with the same ports drives the screen.

## 1. Layout

## 2. Clock and resets

One PC clock, `main_clk` = 100.2273 MHz (2205/22 MHz exactly, VCO 1102.5 MHz,
PFD 20 MHz). It is also the video clock handed to M2M (`video_clk_o`); M2M's
own clocks (QNICE 50 MHz, HyperRAM, HDMI, audio) are untouched.

`pc_system.reset` is a register in `mega65.vhd`, high while any of these is:
the MMCM is not locked, M2M's core or full reset (reset button short/long,
the Shell's CSR reset bit: BIOS loading, the menu's "Reset the PC"), or the
BIOS gate of `pc_bios.vhd` is closed.

## 3. Memory

**System RAM** (`pc_ram.vhd`): two inferred arrays, 512 KB + 128 KB = 160
RAMB36. No QNICE port (Megamiga hard rule 4). The request is registered
before it fans out to the 160 tiles, so read data and `ram_ack` come 2 clocks
after `ram_en` (the contract allows a later ack than 1 clock). The menu's
memory size (640/512/256/128 KB) limits it at run time: above the limit
reads return 0xFF and writes are dropped, both acknowledged.

**BIOS ROM** (`pc_bios.vhd`): 64 KB true dual-port block RAM (16 RAMB36),
QNICE on port A (falling edge), the PC on port B.

- The Shell's ROM auto-loader (`C_CRTROMS_AUTO` in `globals.vhd`, mandatory)
  writes `/pc10/bios.rom` from offset 0 into windows 0..15 while the PC is in
  reset; a missing file is a fatal error of the Shell.
- The device remembers the size (highest written byte + 1). The PC side maps
  `rom_addr` to image byte `(rom_addr + size) mod 65536` and reads 0xFF where
  that sum does not carry, i.e. the image is right-aligned to FFFFF like a
  ROM in the top socket and the space below it is an empty socket.
- Control window `0x0100`: size (offsets 0/1), the gate (2), "file larger than
  64 KB" (3), forget the image (4).
- The firmware's `PREP_START` accepts 8..64 KB and opens the gate; otherwise
  it stops with a fatal message. Size and gate cross into `main_clk` through
  `cdc_stable`; they only change while the PC is in reset.

## 4. Video

`pc_system` gives RGBI `{I, R, G, B}` with `vid_ce` = 14.31818 MHz (every 7th
clock), active-high syncs and blanks that cover them (Megamiga hard rule 6).
`main.vhd` makes 8-bit RGB: 0xAA per colour bit, +0x55 for intensity, and
colour 6 with half green (0x55): the 5153's brown.

- **Analog:** `qnice_scandoubler_o = 1` (15.7 kHz source): VGA at 31.4 kHz,
  640 x 400. The scandoubler uses its plain line doubler
  (`VGA_LINEDOUBLER = true`, needs the clock >= 2x the pixel rate; we have 7x).
  The OSM on the analog path needs a 2x enable: `vid_ce` and 3 clocks later
  (the scandoubler splits the 7-clock pixel the same way). Menu options:
  "Analog: 15 kHz RGB" (scandoubler off, `retro15kHz`) and "Analog: CSYNC".
- **HDMI:** the CGA is a 59.92 Hz source, so only 60 Hz modes are offered:
  720p 60 Hz (default) and 720 x 480 59.94 Hz (`C_VIDEO_HDMI_720_5994`), as
  Megamiga's `ntsc` branch does for its 60 Hz Amiga. ascal scales from the
  15 kHz input; nearest neighbour, no polyphase filter, no triple buffer.
- **OSM canvas:** `VGA_DX x VGA_DY` = 640 x 400 = 40 x 25 characters, the
  picture after the scandoubler. The HDMI overlay shift `H_PIXELS - VGA_DX`
  stays positive for both modes (Megamiga pins 720 because of its 576p mode).

## 5. Keyboard

`keyboard.vhd` watches the framework's round-robin scan of the 80 MEGA65
keys; every change of a mapped key queues its make or break code (16-entry
FIFO). A code goes to `pc_system` as a one-clock `kbd_valid` only while
`kbd_busy` is low, and at least 7 clocks after the previous one so the board's
busy flag can rise. A full FIFO leaves the key's state unchanged, so the
change is seen again on the next scan.

The map (also in the header of `keyboard.vhd` and on the help page):
positional where the MEGA65 has the PC key; `MEGA + 1..0` = F1..F10 (the code
of the make is remembered for the break); F1/F3/F5/F7/F9/F11/F13 = F1..F7;
RUN/STOP = F8; cursor keys = keypad 8/2/4/6 (an 83-key XT keyboard has no
E0 keys); CLR/HOME = keypad 7; RESTORE = Num Lock; NO SCROLL = Scroll Lock.
Not mapped: keypad - . 0 1 3 5 9 (the MEGA65 has no keypad), HELP (opens the
menu), MEGA alone.

The keyboard's power-on self-test answer (0xAA after the BIOS holds the
keyboard clock low) is not in the contract; see section 11.

## 6. Audio

The speaker line becomes 0 or +0x2000 on both channels (a DC-coupled square
wave, like the real speaker). The framework's audio filter is off.

## 7. Menu and firmware

Menu (`config.vhd`, bits = line numbers, `C_MENU_*` in `mega65.vhd`):

```
 PC10-III
 Memory: %s          640 KB / 512 KB / 256 KB / 128 KB
 HDMI: %s            720p 60 Hz 16:9 / 480p 59.94 Hz 4:3
 Analog: 15 kHz RGB
 Analog: CSYNC
 Help
 Reset the PC        momentary: resets through the CSR, unselects itself
 Close Menu
```

Settings file `/pc10/pc10cfg` (the Shell creates it), start folder `/pc10`.

The firmware (`m2m-rom.asm`) is the Shell plus the callbacks; the Megamiga
fork's Shell needs four more than the template's: `HANDLE_CORE_IO`,
`BROWSE_EXTRA`, `CFG_SIGCHECK`, `CFG_SIGSET`. The Shell writes the settings
file with the FAT32 write layer, which is included flat
(`fat32_wglue.asm`), so there are no code banks (`QNICE_CODE_BANKS = ""`).

Budget (`make_rom.sh` prints it; check `HEAP` and `VAR$STACK_START` in
`m2m-rom.lis`):

- ROM: **31305 of 32768 words**; the Shell plus the FAT32 write layer fill
  almost all of it. When it runs out: move the write layer into code banks
  (Megamiga does: banks 1 and 2) or long texts into a read-only data device.
- RAM: `HEAP` = 0xA4FE, `MENU_HEAP_SIZE` 1024 (the 25-line menu needs about
  600; the Shell checks it at boot), `HEAP_SIZE` 19968 (file browser),
  ending at 0xF6FE; the stack (1536 words) starts at 0xFED0, so 466 words
  are left.

`DIP SW1` is a constant in `mega65.vhd` for now: `00101101` (5160 SW1 as the
8255 reads it: no test loop, no 8087, all planar banks, CGA 80 x 25, one
floppy drive).

## 8. The stand-in pc_system

`CORE/stub/pc_system.sv` (module `pc_system`, the contract's ports) lets the
shell be tested on the hardware before the real PC exists:

- CGA raster: 912 dots x 262 lines on `vid_ce` (15.70 kHz, 59.92 Hz), 640 x
  200 active, hsync dots 720-799, vsync lines 224-226;
- text (8 x 8 font from M2M's Anikki ROM): the last scan code and the number
  of codes, the first and the last 16 bytes of the BIOS window (F0000,
  FFFF0: the right alignment is visible there), a RAM test, DIP SW1;
- 16 colour bars (colour 6 must be brown) inside a white one-pixel frame
  (checks cropping/scaling);
- RAM: an endless write-then-verify test of 00000-9FFFF through the memory
  port; with the menu's memory size below 640 KB it reports errors from the
  limit on (that shows the switch working);
- keyboard: `kbd_busy` for 100 us per code, a 100 ms ~1 kHz beep on every
  make code (tests the audio path).

## 9. Build

Firmware only (any Linux machine with cc and awk):

```sh
CORE/m2m-rom/make_rom.sh          # builds qasm into CORE/m2m-rom/.tools first
```

The Vivado pre-synthesis hook runs the same script, so the firmware is always
rebuilt with the bitstream.

Bitstream on the Fedora host (Vivado 2022.2; never stop a Megamiga build
there, ours runs in parallel; see `tools/remote/rbuild.sh`):

```sh
R=tools/remote/rbuild.sh
JOBS=8 $R start ~/git/my/pc10-iii-shell <name> R6   # copy + build_all.sh in the background
$R status <name>
$R wait <name>
$R fetch <name> R6                                   # -> ~/pcxt-work/builds/<name>/
```

`build_bitstream.tcl` fails the run unless WNS/WHS >= 0, `main_clk` has the
9.977 ns period and `pc_ram` still has its 160 block RAMs.

Tests: `tb/shell/run.sh` (ghdl: keyboard codes and the Fn layer, the BIOS
right alignment and gate, RAM latency and size limit; Verilator: the stub's
raster periods, RAM test passes, ROM reader, keyboard strobe). Three mutants
(no right alignment, no break bit, a 1-clock RAM ack) are all caught.

The project file is generated from Megamiga's (framework file list):
`tools/gen_xpr.py <Megamiga>/CORE/CORE-R6.xpr CORE/CORE-R6.xpr`. Only
`VHDL2008` and `SVerilog` file types (Megamiga hard rule 2).

## 10. Results

### The CPU alone (out of context, R6 part xc7a200tfbg484-2, 100.2273 MHz)

`tools/ooc/cpu_ooc.tcl`: MCL86 EU + biu88 + microcode ROM (rtl/cpu at
`40a7663`) with registered I/O, synthesis + place + route.

| | |
|---|---|
| LUTs / FFs | 1856 / 869 |
| Block RAM | 8 RAMB36 (the 8K x 32 microcode ROM) |
| WNS | **-6.567 ns** (368 failing endpoints of 2392; WHS +0.096) |

The CPU does **not** meet 100 MHz: it needs about 16.5 ns, i.e. ~60 MHz.

| Path group | Worst slack | Logic levels |
|---|---|---|
| biu88 -> biu88 (`bus_pending` -> `address_latch` CE) | -6.567 | 22 (LUT6 chain through t_cycle/rphase/fetch_state/ta_cycle/sr_armed) |
| EU microcode ROM output -> biu88 (`ta_cycle`) | -5.461 | 23 (incl. 3 CARRY4) |
| EU ROM output -> EU register file (`eu_register_dx`) | -2.601 | 12 |
| biu88 -> EU | +0.185 | 11 |

217 failing endpoints are in biu88, 151 in the EU. Reports:
`~/pcxt-work/ooc/cpu-ooc-a/`.

### The shell with the stand-in (build `pc10-shell-a`, R6)

Vivado 2022.2 on the Fedora host, default strategies of the Megamiga project
(synthesis defaults, `Performance_ExplorePostRoutePhysOpt`), sources at
`577ef94`. Bitstream and reports: `~/pcxt-work/builds/pc10-shell-a/`
(`mega65_r6.bit`; not loaded on a MEGA65).

| | |
|---|---|
| WNS / WHS | **+0.381 / +0.021 ns** (all constraints met, 0 unrouted nets) |
| main_clk (100.2273 MHz) | +0.416 ns: M2M's analog OSM overlay (`vga_osm`, 14 levels), which runs on the video clock = main_clk |
| LUTs | 20150 (15.1 %) |
| FFs | 14767 (5.5 %) |
| Block RAM | 220.5 of 365 tiles (212 RAMB36 + 17 RAMB18) |
| DSPs | 59 (ascal) |

Where it goes:

| Part | LUTs | Block RAM tiles |
|---|---|---|
| M2M framework (QNICE, ascal, HDMI, OSM, SD, HyperRAM) | 19066 | 43.5 |
| `pc_ram` (640 KB) | 198 | 160 |
| `pc_bios` (64 KB) | 85 | 16 |
| `keyboard` | 267 | 0 |
| stand-in `pc_system` | 453 | 1 |

Against the R3 goal (plan.md section 3: same XC7A200T, 365 tiles): the
framework baseline is 43.5 tiles (the plan guessed 60-70), so RAM + BIOS +
framework = 220 tiles. The real PC adds the CPU (8 RAMB36, ~1.9K LUTs, see
above), the CGA (16-32 KB video RAM + character ROM, ~6-10 tiles) and an
XTIDE ROM (2-4 tiles): about 240 tiles, ~125 left. Even 1 MB of RAM (+96
tiles) would fit. LUTs are no concern (the whole PC will be a few thousand).

The first run of `build_bitstream.tcl` reported `SIGNOFF-FAILED` only
because its own gate counted the block RAMs with a wrong filter (fixed in
`2079271`). The rebuild `pc10-shell-b` (same sources plus that fix) gives the
same timing to the picosecond and `RESULT R6 OK`; its bitstream is
`~/pcxt-work/builds/pc10-shell-b/mega65_r6.bit`.

## 11. Open issues

- **CPU timing** (section 10): biu88's combinational next-state logic and the
  unregistered microcode ROM output feeding both the EU and the BIU. Either
  pipeline (register the ROM output: BRAM output register, one more cycle of
  latency per microinstruction, which the 21:1 ratio could absorb), or use
  the fact that the BIU only acts on `step` (every 21st clock) with
  multicycle constraints - only valid if every path really is gated by
  `step`, which needs a careful audit (the EU talks to the BIU every clock).
- **59.92 vs 60 Hz on HDMI:** ascal drops or repeats a frame about every 13 s
  (no triple buffering in this M2M). A 59.92 Hz HDMI mode (720p with a
  pixel clock of 74.25 x 59.92/60 MHz) would make it smooth; that is a new
  M2M video mode (an M2M-UPSTREAM exception).
- **Keyboard self-test:** the BIOS resets the keyboard (PB6 low ~20 ms) and
  expects 0xAA. Not in the contract; `xt_board` should answer it, or the
  contract gets a `kbd_reset` output so the glue can queue 0xAA.
- **vid_rgbi bit order** (`{I, R, G, B}`) and **dip_sw1 polarity** (bit = 1
  for an open switch, as the 8255 reads it) are not stated in
  architecture.md section 4.
- **The video clock is the 100 MHz PC clock**, so M2M's analog pipeline
  (scandoubler, OSM overlay) and ascal's input side run at 100 MHz, where
  they were made for 28-54 MHz. It closes (+0.416 ns on `vga_osm`), but it
  is the tightest path of the design. The way out if it starts failing: a
  28.63636 MHz video clock (2 x OSC; the line doubler needs >= 2x the pixel
  rate) with a CDC of the RGBI stream. It needs a second MMCM or a
  different VCO: from 1102.5 MHz it is a divide by 38.5, and the only
  fractional output, CLKOUT0, makes main_clk.
- **RAM latency:** the glue answers reads after 2 clocks (registered request
  for the 160-tile fan-out), not 1.
- **Firmware ROM:** 1463 words free (section 7).
- **R3:** this fork's R3 board top was never adapted. It needs:
  - sd-host (exception 18): bidirectional SD pins (CMD, DAT0..3 with output
    enables) from `framework.vhd`, the engine port `sd_eng_*` to the core,
    the pull-ups (CORE.xdc names), both slots;
  - the `MEGA65_Core` port list of R4-R6 (floppy pins are routed already;
    SDRAM, PMOD, Ethernet ports left open or tied - R3 has no SDRAM, so the
    core must not need it, which this shell does not);
  - PMOD (exception 13) only if the serial port is wanted;
  - a `CORE-R3.xpr` (`gen_xpr.py` on Megamiga's R3 project) with `max10.vhdl`
    / `pcm_to_pdm.vhdl` instead of `audio.vhd` (Megamiga hard rule 1).
- Untested on hardware: everything (no bitstream was loaded).
