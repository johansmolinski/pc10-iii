# The MEGA65 shell (M2M) of the PC10-III core

Status: 2026-10-21, branch `m2m-shell`. The framework around `pc_system`
(`rtl/`): clocks, memories, CGA font, floppy images on the SD card, video,
keyboard, audio, menu, firmware, Vivado project and the remote build. The
shell-only stand-in `CORE/stub/pc_system.sv` (same ports) is kept for
experiments without the PC (`tools/gen_xpr.py --stub`).

## 2. Clocks and resets

One MMCM (VCO 1102.5 MHz, PFD 20 MHz), one clock since 2026-10-23
(doc/clock-plan.md):
- `main_clk` = VCO / 38.5 = 28.63636 MHz (315/11 MHz exactly, 2 x OSC): the
  PC, the PC10-III's master clock; also `video_clk`, M2M's video pipeline
  (`video_clk_o`: scandoubler, analog OSM, ascal's input). `main.vhd`
  registers RGBI, syncs, blanks and `vid_ce` (= `ce_14m`) together and hands
  them over as they are.
- Until 2026-10-22: `main_clk` = VCO / 11 = 100.2273 MHz (7 x OSC) for the
  PC and the video pipeline on its own 28.63636 MHz output (a first build
  with the video pipeline on the 100 MHz `main_clk` had failed in M2M's
  `vga_osm`, -1.16 ns).

M2M's own clocks (QNICE 50 MHz, HyperRAM, HDMI, audio) are untouched.

`pc_system.reset` is a register in `mega65.vhd`, high while any of these is:
the MMCM is not locked, M2M's core or full reset (reset button short/long,
the Shell's CSR reset bit: BIOS loading, the menu's "Reset the PC"), the
BIOS gate of `pc_bios.vhd` is closed, or the 8088's microcode has not been
copied into the CPU yet (`pc_ucode.vhd`, section 3).

## 3. Memory

**System RAM** (`pc_ram.vhd`): 20 banks of 32 KB (8 RAMB36 each, 160 in
all). No QNICE port (Megamiga hard rule 4). The request is registered, the
banks read it into their block RAM registers and a multiplexer picks the
bank: read data and `ram_ack` come **2 clocks** after `ram_en` (the board
waits for `ram_ack`; doc/timing.md section 2.10 shows why the board does not
see it). On the 100.2273 MHz clock the request needed a register set per
group of banks and per bank and the outputs two more stages (6 clocks): with
the request fanning out to 160 tiles from one register the first real-PC
build missed by up to 3.3 ns. At 28.63636 MHz (34.9 ns) one register each
way is plenty. The menu's memory size
(640/512/256/128 KB) limits it at run time: above the limit reads return 0xFF
and writes are dropped, both acknowledged. `tb/sys` boots GLaBIOS with a
3-clock RAM model (section 9).

**BIOS ROM** (`pc_bios.vhd`): 64 KB true dual-port block RAM (16 RAMB36),
QNICE on port A (falling edge), the PC on port B.

- The Shell's ROM auto-loader (`C_CRTROMS_AUTO` in `globals.vhd`, mandatory)
  writes `/pc10/bios.rom` from offset 0 into windows 0..15 while the PC is in
  reset; a missing file is a fatal error of the Shell.
- The device remembers the size (highest written byte + 1). The firmware's
  `PREP_START` (`BIOS_ALIGN`) moves an image smaller than 64 KB to the top, so
  that it ends at FFFFF like a ROM in the top socket, and fills the space
  below it with 0xFF (an empty socket); the PC reads the RAM 1:1, without an
  adder in the 1-clock ROM path (it cost 0.24 ns in the first build).
- Control window `0x0100`: size (offsets 0/1), the gate (2), "file larger than
  64 KB" (3), forget the image (4).
- The firmware's `PREP_START` accepts 8..64 KB, aligns it and opens the gate;
  otherwise it stops with a fatal message. The gate crosses into `main_clk`
  through `cdc_stable`; it only changes while the PC is in reset.

**CGA character ROM** (`pc_font.vhd`): the CGA card's font RAM has no initial
contents, so the glue keeps an 8 KB image (2 RAMB36, 5788005 layout) and
copies it into `pc_system`'s font port, one byte per clock:
- preloaded with a free default font, `CORE/font/cga_default.hex`: GLaBIOS's
  8x8 glyphs 00-7F (VileR's font, CC BY-SA 4.0, attribution in
  `CORE/font/README.md`), 80-FF empty, a thinned copy as the thin font. It is
  generated by `tools/mkcgafont.py` from the GLaBIOS source and committed,
  because the build host has no GLaBIOS checkout;
- copied after every main reset (power-up);
- `/pc10/cga.rom` (optional auto-load ROM) overwrites the image; `PREP_START`
  (`FONT_START`) checks the size (2 KB = 8x8 only, copied to 0x1800 and as the
  thin font to 0x1000; 8 KB = the whole ROM) and asks for a new copy;
- `CGA: thin font` in the menu is the card's jumper P3 (`font_thin`).

**The 8088's microcode** (`pc_ucode.vhd`, 2026-10-22): the CPU (z8086's EU,
doc/z8086.md) runs Intel's microcode, which is neither in the repository nor
in the bitstream (AGENTS.md rule 4). The user builds the bundle once with
`tools/mkucode.py` from his own copy of Andrew Jenner's public archive and
puts it on the SD card next to the BIOS:

```sh
curl -O https://www.reenigne.org/misc/8086_microcode_v2.zip && unzip 8086_microcode_v2.zip
python3 tools/mkucode.py --jenner 8086_microcode_v2 -o ucode.bin   # -> /pc10/ucode.bin
```

- `/pc10/ucode.bin` is a mandatory auto-load ROM (`globals.vhd`): a missing
  file is the Shell's fatal "file not found" screen, like a missing BIOS.
- The glue keeps the 6 KB file in an 8 KB block RAM (2 RAMB18, no initial
  contents) on QNICE's side; `PREP_START` (`UCODE_START`) checks the size
  (6144 bytes, not larger), the magic `PC10UCOD`, the version, the size field
  and the checksum (the sum of the bytes 0x0100..0x17FF), reading the image
  back, and stops with "/pc10/ucode.bin is not a valid 8088 microcode bundle
  (tools/mkucode.py)" otherwise.
- Then it writes GO (control window `0x0100`, offset 2): the glue copies the
  image into `pc_system`'s load port (`ucl_we/ucl_addr/ucl_data`, one byte
  per `main_clk`, 6144 clocks) and only then opens the microcode gate, which
  releases the PC's reset together with the BIOS gate. The CPU's tables keep
  their contents over PC resets. Offsets 0/1 read the size and "larger than
  8 KB", offset 4 forgets the image (gate closed).
- Format: `tools/mkucode.py`'s header; the CPU side: doc/z8086.md section 3.

## 4. Floppy drives A: and B:

The FDC card (`rtl/fdc`, doc/fdc.md) asks for whole 512-byte sectors through
the sector port and buffers them itself, so the backend (`pc_fdd_sd.vhd`)
needs no cache. It follows Megamiga's floppy-direct approach (`adf_sd.vhd`):
the images stay on the SD card and the hardware moves single blocks through
the SD host controller's engine port (M2M exception 18); the firmware only
resolves the file.

- **Mount:** the menu lines ` A:%s` / ` B:%s` are manual ROM loads 0/1 into
  `C_DEV_PC_FDA`/`FDB`. `PREP_LOAD_IMAGE` switches the drive off, checks the
  size (160K, 180K, 320K, 360K, 720K), writes the extent map
  (`FAT32$FILE_MAP`, up to 511 extents) into the device's window 1, then the
  number of sectors, the block of cluster 0, log2(sectors per cluster) and the
  card slot, mode last (`FD_SETUP`, after Megamiga's `ADF_TB_SETUP`), and
  leaves the file pointer at the end, so the Shell streams nothing. The
  device answers the Shell's CSR handshake itself.
- **Geometry** from the number of sectors (doc/fdc.md section 5); an image of
  another size is "no disk". `drv_80trk` follows the image (an 80-track drive
  for 720K).
- **Read:** the request crosses into the QNICE clock domain (toggle, stable
  payload); the LBA becomes an SD block through the extent map (walked in
  hardware, ~6 clocks per extent); one block is read through the engine port
  into a 512-byte dual-port buffer and streamed to the card, then `sp_done`.
- **Write:** the card's 512 bytes go into the buffer first (`sp_wr_ready` =
  1), then the block is written; `sp_done` when it is on the card
  (write-through: a completed WRITE DATA is in the image file).
- **Errors:** an engine error is retried twice, 1 ms apart; a controller that
  is not ready is waited for up to 500 ms; a transfer that QNICE preempted
  before its block is issued again. A drive that is off, an LBA beyond the
  file, an engine failure or a write to a protected drive end with `sp_err`
  (the 765 then reports a data error / general failure).
- **Write protection:** `A: write protected` / `B: write protected` in the
  menu (the FDC's WP and the backend's refusal).
- **Drive LED** (`pc_drvsnd.vhd`, since 2026-10-25): yellow (Megamiga's
  floppy colour) while drive A: or B: is selected, i.e. the DOR selects it
  and its motor bit is set (`drv_select` from `fdc_card.sv`). That is the
  drive select line of the real adapter, which lights the front-panel LED of
  a PC10-III's 5.25" drive: it stays on while the motor runs on after an
  access (about 2 s with the BIOS: the select bits still point at the
  drive), and it is off while only the other drive's motor runs, or for
  select bits without the drive's motor bit. (Until 2026-10-25:
  green while a motor ran or the FDC executed, yellow while a block moved to
  or from the SD card.)

### Drive sound (the internal drive)

Megamiga 0.7's "Virtual Drive Sound" (its `hwf_pins_proc`, the disk guard
of 90f1e9b), ported to `pc_drvsnd.vhd`: the MEGA65's internal 3.5" drive
plays the sounds of the image drives. Menu: `Drive sound (int. drive)`
(default on; Megamiga's third choice "Noclick" has nothing to do here: a PC
selects a drive only with its motor on, so there are no clicks of an empty
drive without the motor).

- **Motor:** runs while the DOR's motor bit of A: or B: is set.
- **Steps:** one step pulse for every cylinder the selected drive's head
  moves (`drv_step`, `drv_step_in` from `fdc_card.sv`): that is one per 765
  step pulse, at the 765's step rate (SPECIFY's SRT; 6 ms with the XT BIOS),
  as the real drive takes them. A 360K image is in a 40-track drive, so a
  seek moves the real head as many tracks as a 40-track drive moves its own
  (a seek to cylinder N: N steps, the sound of the 40-track drive). The 765's
  pulses beyond the emulated drive's stop (the PC10-III BIOS's seek to
  cylinder 50 at POST, its probe for an 80-track drive, stops the 40-track
  head at 41) move nothing there and give no step here, so the real head
  stays where the emulated one is and the recalibrate brings both back to 0.
- **The real head** is followed in `cyl` (0..79): an inward step at 79 is not
  passed on, an outward one neither at 0 nor while the drive reports TRK0
  (then `cyl` := 0; only after an outward step, because a drive still
  reports track 0 for a few ms after stepping in from it). Its position is
  unknown at power-up: before the first step, as soon as a PC motor runs,
  the drive is **homed** (outward steps every 6 ms until TRK0, at most 85),
  the sound of a PC's POST recalibrate; PC steps during the homing are not
  passed on.
- **Pulses:** direction set, 8 us, step low 8 us, direction held 8 us (the
  drive needs about 1 us each); a step during a pulse (overlapped seeks of
  both drives) is dropped and not counted.
- **Disk guard:** a real disk in the drive silences it, so it is never
  worn. While the drive is selected, /DSKCHG is valid after 36 us (1031
  clocks), and high means a disk is in: the drive clears its change latch on
  a step with a disk inserted, so the first step after an insertion finds it
  (until then the motor may run with the disk, as in Megamiga). Then: no
  motor, no steps, only a probe every 2^24 clocks (0.586 s) of 2^13 clocks
  (286 us) selected; a low /DSKCHG (the disk was taken out) brings the sound
  back. A step goes out only after the 36 us, so the guard has looked first.
- Write gate, write data, side and density stay inactive (density: the
  DD-safe level), f_motorb/f_selectb are tied at the top level. Off in the
  menu: the drive is never selected (no probe either).
- Timing constants (main_clk 28.63636 MHz, Megamiga's at 28.375 MHz in
  brackets): settle 1031 clocks = 36.0 us (1023 = 36.05 us), probe period
  2^24 = 0.586 s (0.591 s), probe 2^13 = 286 us (289 us), step pulse /
  direction setup / hold 229 = 8.0 us (Megamiga passes the Amiga's own
  pulses), homing 171818 = 6.000 ms.

## 5. Video

`pc_system` gives RGBI `{I, R, G, B}` changing once per dot (every 7th main
clock), active-high syncs and blanks that cover them (Megamiga hard rule 6).
`main.vhd` takes them into `video_clk` every video clock: a dot is exactly 2
video clocks, so every dot is seen twice and a free-running `video_ce` at
every second video clock (14.31818 MHz) picks it once; the crossing is a
synchronous path between the two related clocks. 8-bit RGB: 0xAA per colour
bit, +0x55 for intensity, and colour 6 with half green (0x55): the 5153's
brown. The CGA's visible window is MartyPC's "Full" aperture, 768 x 245
(doc/cga.md section 6.6): exactly the scandoubler's 768-dot line buffer.

- **Analog:** `qnice_scandoubler_o = 1` (15.7 kHz source): VGA at 31.4 kHz,
  768 x 490. The scandoubler uses its plain line doubler
  (`VGA_LINEDOUBLER = true`, needs the clock >= 2x the pixel rate: exactly 2x
  now, as in Megamiga); the analog OSM's 2x enable is every video clock.
  Menu options: "Analog: 15 kHz RGB" (scandoubler off, `retro15kHz`) and
  "Analog: CSYNC".
- **HDMI:** the CGA is a 59.92 Hz source, so only 60 Hz modes are offered:
  720p 60 Hz (default) and 720 x 480 59.94 Hz (`C_VIDEO_HDMI_720_5994`), as
  Megamiga's `ntsc` branch does for its 60 Hz Amiga. ascal scales from the
  15 kHz input; nearest neighbour, no polyphase filter, no triple buffer.
- **OSM canvas:** `VGA_DX x VGA_DY` = 640 x 400 = 40 x 25 characters, the
  picture after the scandoubler. The HDMI overlay shift `H_PIXELS - VGA_DX`
  stays positive for both modes (Megamiga pins 720 because of its 576p mode).

## 6. Keyboard

`keyboard.vhd` watches the framework's round-robin scan of the 80 MEGA65
keys (pipelined in three stages for 100 MHz; after a change the next two
clocks are ignored, so a key's stale state is never acted on); every change
of a mapped key queues its make or break code (16-entry FIFO). A code goes to `pc_system` as a one-clock `kbd_valid` only while
`kbd_busy` is low, and at least 7 clocks after the previous one so the board's
busy flag can rise. A full FIFO leaves the key's state unchanged, so the
change is seen again on the next scan.

The map (also in the header of `keyboard.vhd` and on the help page):
positional where the MEGA65 has the PC key; `MEGA + 1..0` = F1..F10 (the code
of the make is remembered for the break); F1/F3/F5/F7/F9/F11/F13 = F1..F7;
RUN/STOP = F8; cursor keys = keypad 8/2/4/6 (an 83-key XT keyboard has no
E0 keys); CLR/HOME = keypad 7; RESTORE = Num Lock; NO SCROLL = Scroll Lock.
Not mapped: keypad - . 0 1 3 5 9 (the MEGA65 has no keypad), HELP (opens the
menu), MEGA alone.

The keyboard's power-on self-test answer (0xAA) comes from `xt_board`
(architecture.md section 4).

## 7. Audio

The speaker line becomes 0 or +0x2000 on both channels (a DC-coupled square
wave, like the real speaker). The framework's audio filter is off.

## 8. Menu and firmware

Menu (`config.vhd`, bits = line numbers, `C_MENU_*` in `mega65.vhd`):

```
 PC10-III
 A:%s                the floppy image of A: (file browser), "<No Disk>"
 B:%s                the floppy image of B:
 A: write protected
 B: write protected
 Drive sound (int. drive)  the internal drive plays A:/B:'s sounds (default on, section 4)
 Chipset: %s         PC10-III (FE2010A) (default) / IBM XT (8255); a change restarts the PC
 Memory: %s          640 KB / 512 KB / 256 KB / 128 KB
 HDMI: %s            720p 60 Hz 16:9 / 480p 59.94 Hz 4:3
 CGA: thin font      jumper P3
 Analog: 15 kHz RGB
 Analog: CSYNC
 Help
 Reset the PC        momentary: resets through the CSR, unselects itself
 Close Menu
```

Settings file `/pc10/pc10cfg` (the Shell creates it), start folder `/pc10`.
It holds one byte per menu line, so its layout is the menu's: since
2026-10-25 the firmware's `CFG_SIGCHECK` accepts a file only when its text
(M2M-UPSTREAM cfg-strings, behind the menu bytes) has the line `menu=3`
(`CFG_SIG_VAL` in `m2m-rom.asm`, the layout version: change it with every
change of the menu's lines; `2` was the 32-line menu with the drive sound,
`3` the 39-line one with the chipset submenu). Any other file (the 31-line
files before the drive sound line had none; the Shell would even load a
shorter file as one from a menu that grew at its end, shifting every option
behind the new lines) gets the defaults, and `CFG_SIGSET` writes the
signature with the next save (when the menu closes).

**Chipset** (2026-10-25, `pc_chipset.vhd`): the PC10-III's Faraday FE2010A
(default; the Commodore BIOS 4.41 needs it) or the IBM 5160's 8255 (GLaBIOS,
the free BIOS, selects the switch nibble with PB3 like a 5160 and stops with
"POST Error 0800 FDD" on the FE2010A). `xt_board.sv` has both port logics and
takes its `fe2010a` input while the PC is in reset; the switches follow the
chipset (5D FE2010A, 6D 8255, see below). A change of the menu item holds the
PC in reset for 2^16 clocks (2.3 ms) from the clock the menu bit changes, so it
restarts the PC with the new chipset and switches (the memory size, in
contrast, acts at once: `pc_ram.vhd` limits the RAM live).

The firmware (`m2m-rom.asm`) is the Shell plus the callbacks (`PREP_START`:
BIOS check, alignment and gate, CGA font; `PREP_LOAD_IMAGE`: the floppy
images; `OSM_SEL_POST`: the momentary reset); the Megamiga fork's Shell needs
four more than the template's: `HANDLE_CORE_IO`,
`BROWSE_EXTRA`, `CFG_SIGCHECK`, `CFG_SIGSET`. The Shell writes the settings
file with the FAT32 write layer, which is included flat
(`fat32_wglue.asm`), so there are no code banks (`QNICE_CODE_BANKS = ""`).

Budget (`make_rom.sh` prints it; check `HEAP` and `VAR$STACK_START` in
`m2m-rom.lis`):

- ROM: **32037 of 32768 words** (731 free; 31991 before the settings
  signature); the Shell plus the FAT32 write
  layer fill almost all of it. When it runs out: move the write layer into code banks
  (Megamiga does: banks 1 and 2) or long texts into a read-only data device.
- RAM: `HEAP` = 0xA51A, `MENU_HEAP_SIZE` 1024 (the 39-line menu needs 806:
  20 + 448 item characters + 1 + 4 x 39 + 1 + (3 submenus + 2 manual ROMs +
  1) x 30; the Shell checks it at boot), `HEAP_SIZE` 19968 (file browser),
  ending at 0xF71A; the stack (1536 words) starts at 0xFED0, so 438 words
  are left.

`DIP SW1` follows the chipset (`C_DIP_SW1_FE`/`_XT` in `mega65.vhd`): 0x6D for
the 8255 (5160 SW1 as the 8255 reads it: no test loop, no 8087, all planar
banks, CGA 80 x 25, two floppy drives; tb/sys's default), 0x5D for the FE2010A
(bits 5-4 are its VID pins, the PC10-III's CONFIG switches 3 and 4: 01 = 80 x 25
colour for the Commodore BIOS, which swaps 01/10; the other bits are the reset
value of its switch register; tb/sys `make FE=1` with `-d 5D`).

## 9. The stand-in pc_system

`CORE/stub/pc_system.sv` (module `pc_system`, the contract's ports; font and
floppy ports ignored) lets the shell be tested without the PC
(`tools/gen_xpr.py --stub ...`):

- CGA raster: 912 dots x 262 lines on `vid_ce` (15.70 kHz, 59.92 Hz), 640 x
  200 active, hsync dots 720-799, vsync lines 224-226;
- text (8 x 8 font from M2M's Anikki ROM): the last scan code and the number
  of codes, the first and the last 16 bytes of the BIOS window (F0000,
  FFFF0: the right alignment is visible there), a RAM test, DIP SW1;
- 16 colour bars (colour 6 must be brown) inside a white one-pixel frame
  (checks cropping/scaling);
- RAM: an endless write-then-verify test of 00000-9FFFF through the memory
  port; with the menu's memory size below 640 KB it reports errors from the
  limit on (that shows the switch working);
- keyboard: `kbd_busy` for 100 us per code, a 100 ms ~1 kHz beep on every
  make code (tests the audio path).

## 10. Build

Firmware only (any Linux machine with cc and awk):

```sh
CORE/m2m-rom/make_rom.sh          # builds qasm into CORE/m2m-rom/.tools first
```

The Vivado pre-synthesis hook runs the same script, so the firmware is always
rebuilt with the bitstream.

Bitstream on the Fedora host (Vivado 2022.2; never stop a Megamiga build
there, ours runs in parallel; see `tools/remote/rbuild.sh`):

```sh
R=tools/remote/rbuild.sh
JOBS=8 $R start ~/git/my/pc10-iii-shell <name> R6   # copy + build_all.sh in the background
$R status <name>
$R wait <name>
$R fetch <name> R6                                   # -> ~/pcxt-work/builds/<name>/
```

`build_bitstream.tcl` writes the bitstream in any case and prints one
`RESULT` line: `SIGNOFF-FAILED` (a gate), `TIMING-FAILED` (WNS or WHS < 0)
or `OK`. Gates: `main_clk` 34.921 ns (the one PC clock since clk28; the old
`video_clk` and the floppy geometry's multicycle target are gone), `pc_ram` has its
160 block RAMs. It also writes
`utilization_hierarchical.rpt` and `worst_paths.rpt` (50 paths, one per
group) next to the bitstream; `rbuild.sh fetch` copies them.

**Reference builds:** `REF=<earlier build> rbuild.sh start ...` (build_all.sh
`REF_DIR`) runs incremental synthesis and implementation from that build's
checkpoints (keep its tree on the host). Vivado only does it when the
reference is close to timing: with a reference at WNS < -1.0 ns it falls back
to a normal run (`Reference DCP WNS -6.415 ns is less than the threshold
value -1.000 ns`, build `pc10-real-c`). So the first build with the CPU
timing fix is a full one, later ones can use it as their reference.

## 12. Open issues

- **Timing:** see section 11. The CPU (cpu-timing branch). Everything else
  (the 8237 path of the board, the 8253, the FDC, the paths out of the
  board's and the CPU's combinational outputs into the FDC, the BIOS ROM
  address and `pc_ram`) closes since branch board-timing: doc/timing.md.
- **Reference builds** need a reference within -1.0 ns WNS (section 10):
  rebuild in full once the CPU fix is merged, then use that build as `REF=`.
- **Drive sound on hardware:** the real drive's step rate limit (the 765
  steps at SRT; a fast program's 2-3 ms could be too fast for the 3.5" drive,
  which then loses steps: only sound, the counter would be off until the next
  TRK0), its TRK0 delay, and the /DSKCHG behaviour of the MEGA65's drive (the
  guard relies on it as Megamiga does) are untested here.
- **Not on hardware:** nothing of this has run on a MEGA65 (no bitstream was
  loaded). Untested in simulation: the firmware (QNICE), i.e. BIOS_ALIGN,
  FONT_START, PREP_LOAD_IMAGE/FD_SETUP, the menu; the M2M CSR handshake of
  the floppy devices; the SD engine port with the real `sdhost.vhd` (the
  bench uses a model of its protocol).
- **Floppy images:** no eject (Megamiga ejects with SPACE in the menu; here a
  drive keeps its image until another is chosen); the images are not
  remembered across power-up (Megamiga's profiles keep paths in the settings
  file text, M2M exception 17); a changed SD card is not noticed (Megamiga
  re-checks the card generation, `ADF_SD_GEN`); 1.2M/1.44M need the AT
  controller (doc/fdc.md section 7).
- **The default font** has only 128 glyphs (80-FF empty).
- **59.92 vs 60 Hz on HDMI:** ascal drops or repeats a frame about every 13 s.
  A 59.92 Hz HDMI mode would be a new M2M video mode (an M2M-UPSTREAM
  exception).
- **Firmware ROM:** 32037 of 32768 words; the next features need code banks
  (Megamiga puts the FAT32 write layer into banks 1 and 2).
- **R3:** this fork's R3 board top was never adapted. It needs:
  - sd-host (exception 18): bidirectional SD pins (CMD, DAT0..3 with output
    enables) from `framework.vhd`, the engine port `sd_eng_*` to the core
    (the floppy backend uses it), the pull-ups (CORE.xdc names), both slots;
  - the `MEGA65_Core` port list of R4-R6 (floppy pins are routed already;
    SDRAM, PMOD, Ethernet ports left open or tied - R3 has no SDRAM, so the
    core must not need it, which this core does not);
  - PMOD (exception 13) only if the serial port is wanted;
  - a `CORE-R3.xpr` (`gen_xpr.py` on Megamiga's R3 project) with `max10.vhdl`
    / `pcm_to_pdm.vhdl` instead of `audio.vhd` (Megamiga hard rule 1).
