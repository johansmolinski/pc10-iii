# The 8088: z8086's EU with Intel's microcode

Status: 2026-10-22, branch `z86`. The PC10-III's CPU (`rtl/cpu/cpu8088.sv`,
`CPU = "z86"`, the default): nand2mario's z8086 execution unit running Intel's
own 8088 microcode, one microinstruction per 8088 clock, in front of `biu88`.
The evaluation that led here is doc/z8086-eval.md.

## 1. Pieces

| File | What |
|---|---|
| `rtl/cpu/z8086/z86_eu.sv` | z8086's EU (sequencer, loader, M/N, registers, ALU); every register changes only at its clock enable |
| `rtl/cpu/z8086/alu.sv` | z8086's ALU (DAA/DAS threshold and NEG byte carry corrected) |
| `rtl/cpu/z8086/z86_tables.sv` | the four Intel tables as RAMs, loaded from the bundle; the overlay |
| `rtl/cpu/z8086/z86_overlay.svh` | the 8088 interrupt overlay for an 8086 ROM (section 5) |
| `rtl/cpu/z8086/cpu_z86.sv` | EU + tables + biu88, INTR/NMI/TEST sampled at the clock edge |
| `rtl/cpu/biu88.sv` | the cycle-stepped BIU (MartyPC's model) with the real chip's EU/BIU interface |
| `tools/mkucode.py` | builds the microcode bundle from the user's own copy of the public data |
| `CORE/vhdl/pc_ucode.vhd` | the core: the bundle from the SD card into the CPU (doc/m2m-shell.md section 3) |

## 2. Rule 4: where Intel's tables come from

The EU needs four tables that were read off Intel's die:

1. the microcode ROM, 512 words of 21 bits;
2. the ROM's address decoder ("compression"): a 13-bit microcode address
   `{AR, CR}` selects one of 128 rows of four words;
3. the translation ROM: the entry points of the effective-address routines and
   the targets of the long jumps and calls;
4. the group decode ROM: 15 instruction-class signals per opcode (and for the
   interrupt pseudo-opcode 0x100).

None of them is in the repository or in the bitstream (AGENTS.md rule 4).
z8086 itself carries 2-4 as logic (`group_decode`, `translate`, `uaddr_pack`
in its `z8086.sv`); those functions are gone from `z86_eu.sv`, and upstream's
`z8086.sv` was removed. All four are RAMs (`z86_tables.sv`) without initial
contents, filled at start-up from the **microcode bundle**, which the user
builds with `tools/mkucode.py` from his own copy of Andrew Jenner's archive
`8086_microcode_v2.zip` (https://www.reenigne.org/misc/8086_microcode_v2.zip,
"8086 microcode disassembled": bit images of the ROMs from Ken Shirriff's die
photos). The tool contains no table data; it decodes the bit images the way
Jenner's XTCE does (`xtce_microcode.h`, The Unlicense).

**The archive has the 8088 ROM.** Besides the 8086 images (`l0a.txt` ..
`r3a.txt`, `translation_8086.txt`) it has the 8088's (`l0.txt` .. `r3.txt`,
`translation_8088.txt`); XTCE loads those for the 8088. The evaluation had
missed this (it looked for a separate dump). `mkucode.py --cpu 8088` (the
default) builds a genuine 8088 bundle, which is what the core and the
testbenches use. Checked: Jenner's 8086 images give exactly z8086's
`ucode.hex` (`--ucode-hex` compares them); the decoder, translation and group
tables decoded from the archive equal z8086's functions entry for entry (the
group ROM's rows are the complements of z8086's signals); the 8088 ROM
differs from the 8086's in 11 words, all in the interrupt routines, and the
8088 translation ROM in the INTR entry (0x19E instead of 0x19D).

## 3. The bundle

`tools/mkucode.py --jenner DIR [--cpu 8088|8086] [--ucode-hex FILE] -o OUT`,
`--check FILE` verifies one. Version 1, little endian, 6144 bytes:

| Offset | Size | Content |
|---|---|---|
| 0x0000 | 8 | magic `PC10UCOD` |
| 0x0008 | 1 | version (1) |
| 0x0009 | 1 | flags: bit 0 genuine 8088 ROM (the overlay is off), bit 1 8086 ROM |
| 0x000A | 2 | size (0x1800) |
| 0x000C | 2 | checksum: sum of the bytes 0x0100..0x17FF modulo 65536 |
| 0x0010 | 32 | description (ASCII) |
| 0x0200 | 512 | translation ROM: 256 x u16, index `{mode_rm[4:0], mem_read_not, is_mem, disp_not}` -> `{AR, CR}` |
| 0x0400 | 1024 | group decode: 512 x u16 (15 signals, z8086's order and polarity), index = opcode, 0x100 = interrupt |
| 0x0800 | 2048 | address decoder: 2048 x u8, `{AR, CR}[12:2]` -> row group 0..127 |
| 0x1000 | 2048 | microcode: 512 x u32 (21 bits), row = 4 x group + `CR[1:0]` |

Where it lives:
- **MEGA65:** `/pc10/ucode.bin` on the SD card, next to `/pc10/bios.rom`
  (doc/m2m-shell.md section 3: auto-loaded, checked by the firmware, copied into
  the CPU, the PC held in reset until then).
- **Simulation** (`tb/sst`, `tb/sys`): `$PC10_UCODE`, else the path compiled in
  (`make Z86_UCODE=...`, default `~/pcxt-work/ucode/8088.bin`). The C++ drivers
  check it like the firmware (`tb/common/ucode_file.h`) and stream it through
  the CPU's load port in reset.

The CPU's load port (`cpu8088`/`pc_system` `ucl_we/ucl_addr/ucl_data`, on
`clk`): the byte at bundle offset `ucl_addr`; `z86_tables.sv` picks the table
by the offset. The microcode word is read in two clocks (decoder, then ROM,
both block RAMs) from `{AR, CR}`, which the EU changes only at its enable and
takes at the next one.

## 4. Interrupts and the rest of the pins

At an instruction boundary (the loader's first clock, FC, which with an
interrupt pending does not wait for a queue byte, as XTCE's `readOpcode`):

- **NMI**: a rising edge, sampled at the 8088 clock edge, pending until taken.
- **INTR**: sampled at the 8088 clock edge; taken when IF is set and was set at
  the start of the instruction that ends there (one more instruction after
  STI, POPF or IRET that set IF; MartyPC's `interrupt_inhibit`).
- **Single step**: TF at the start of the instruction that ends (an
  instruction that sets TF is not trapped, one that clears it is).
- None of them after a prefix or a segment register load (MOV sr, POP sr:
  XTCE's "load segment register" group), so prefixes stay with their
  instruction and SS:SP loads stay together.
- Priority NMI, INTR, single step (MartyPC). The routine starts at
  `1r0000000.00ab` (single step, NMI, INTR: XTCE 0x1000-0x1002) with the group
  ROM's entry 0x100.
- The microcode's **INT** jump condition (REP string instructions, WAIT) is
  NMI pending or INTR with IF (XTCE); **TEST** is the -TEST pin (high = not
  asserted: WAIT waits; the board ties it high).
- **INTA**: the 8088 routine's one interrupt-acknowledge access is a word
  request; biu88 makes the two INTA bus cycles of it, LOCK low between them,
  and returns the second byte (the vector).
- **LOCK**: from the LOCK prefix to the start of the instruction after the
  locked one (XTCE); with biu88's INTA LOCK on the pin. (z8086 took F0 for a
  REP prefix; fixed.)
- **HLT**: no instruction starts until an interrupt is taken; biu88 stops
  prefetching, lets the running bus cycle finish, runs one Ti and makes the
  halt cycle: status 011 in a T1 with ALE (MartyPC's `biu_halt`), then
  passive. Not compared with a trace (GLaBIOS does not halt in the traced
  time; the suite has no HLT).

## 5. The 8088 interrupt overlay

For an 8086 bundle (`--cpu 8086`, e.g. from z8086's `ucode.hex`) the tables
module replaces the interrupt words whose behaviour differs on the 8088 with
its own (`z86_overlay.svh`); with a genuine 8088 bundle (flag bit 0) it is off.

The words are ours, written from documented behaviour, before and without
looking at the 8088 ROM's words; they hold only what differs, not the 8086's
words. Sources:
- Jenner, "8086 microcode disassembled" (reenigne.org): the differences are in
  the interrupt handling; the 8086 makes two INTA accesses, the 8088 one,
  which its BIU splits; the 8088's INTR translation entry is 0x19E.
- MartyPC (MIT), `cpu_808x/interrupt.rs`: the 8088's sequences and their cycle
  counts per routine (hardware interrupt, INTR routine, INT0/1/2/3, INTO), the
  suspend after the vector reads.
- The SingleStepTests 8088 traces (hardware captures) of CC, CD, CE and the
  divide errors (F6.6, F6.7, F7.6, F7.7, D4): where the vector reads and the
  pushes fall, the code fetch between the two vector words.

Derivation:
1. One INTA access: the hardware path's second INTA word (row 0x19C) does
   nothing.
2. INTR at 0x19E: the software interrupts enter past 0x19D, where the 8086
   moves the number from OPR to tmpb. So the entry words must leave the number
   in tmpb: rows 0x198 (single step), 0x199 (NMI) and 0x1A7 (INT 0) put CR (the
   interrupt number at these rows) into tmpb and jump to 0x19E; rows 0x1AF
   (INTO) and 0x1B2 (INT 3) do the same with the long jump INTR; the
   translation entry INTR is 0x19E.
3. INT n: the SST CD traces (prefetched case) start the first vector read two
   clocks earlier than the 8086 sequence (immediate, then a separate jump)
   gives: the immediate goes to tmpb in the same word as the long jump INTR
   (row 0x1A8).
4. Prefetching continues during the vector reads (CD: a code fetch between the
   vector words) and is suspended after them (MartyPC: after the CS read): the
   hardware path's 0x19D moves the vector to tmpb's low byte without the
   8086's suspend, and the move after the CS read (row 0x1A3) adds it.
Check of the cycle counts against MartyPC's sequences: INT 3 and INTO reach
0x19E in the same number of clocks (MartyPC's labels differ, the totals
agree); INT 0 one clock less than through 0x19D, as MartyPC's `skip_first`.

Result (section 7): with the 8086 bundle and the overlay the full suite is the
same as with the genuine 8088 bundle. The hardware interrupt path (rows
0x19A-0x19D) is not in the suite; it runs in `tb/sys` (the 8259's IRQs)
against MartyPC's trace with the genuine bundle.

## 6. Clocking and the EU/BIU interface

Phase B (2026-10-22): biu88 has the real chip's EU/BIU split; the MCL86
command layer and biu88's per-core-clock "fast part" are gone (the old BIU
went with MCL86, see doc/history.md).

- biu88 steps at `step` (the rising CLK edge) and changes state there only:
  it takes the EU's events of its last clock, then runs this clock's cycle
  (MartyPC's `cycle()`: do_cycle, the address cycle, the request phases).
  Its outputs are registers set at the step.
- The EU runs at `step` + 3 clk (`EU_DELAY`; every clk in reset) and changes
  state there only; it reads biu88's outputs (after the step) and sets its
  own outputs, which biu88 takes at the next step. So the order per 8088
  clock is MartyPC's: cycle, EU actions, cycle...
- EU -> BIU, per 8088 clock: the queue read (`q_rd`, first byte or not), and
  at most one of: a request (read/write, memory/I/O/INTA, byte/word, segment
  code + offset, data), FLUSH (the new IP), SUSP, HALT; the LOCK prefix
  level. biu88 reads the segment registers from the EU.
- BIU -> EU: the queue head and empty flag, the EU's IP, the T-state (for
  CORR), `done` (a read whose last T4 begins, a write whose last T3/Tw
  begins with READY, a SUSP with no fetch running or the fetch in T4),
  `done_imm` (done in the step that took the request: an immediate SUSP) and
  the read data. The EU keeps `bus_busy` itself and resumes as XTCE: in the
  done clock for a read and for the RNI of a W,RNI, a clock later for a
  write or a SUSP that waited.
- The pins (AD, S2-S0, QS, ALE, LOCK) and `bus_t`/`bus_type` for the board
  come from biu88's step registers; READY and the data bus are sampled at the
  step. Nothing in the CPU needs a clock faster than the 8088's beyond
  `EU_DELAY` and the enables (doc/clock-plan.md).
- `rtl/cpu/cpu8088.xdc`: every EU or biu88 register to every EU or biu88
  register is a 3-clock multicycle path (biu88 -> EU is exactly EU_DELAY, the
  others at least 18 clk).

## 8. Harness mapping (`tb/sst/tb_z86.v`)

`dbg_eu_cmd` shows the EU's FLUSH as MCL86's flush request (the loader's JMP
FAR, where the harness installs a prefetched queue; biu88 takes the preload
at the next step, after the flush), `dbg_rom_addr` 0x0006 while the loader waits for an
opcode (where a prefetched queue is installed), `dbg_dispatch` one EU clock
after FC and after an outstanding transfer, `dbg_ip` the EU IP at FC,
`dbg_flags` with bit 1 cleared.
